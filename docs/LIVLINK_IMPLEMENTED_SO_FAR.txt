LIVLINK — IMPLEMENTED SO FAR
Updated: 17 September 2026

1. PRODUCT OVERVIEW

LIVLINK is an Integrated Smart Living Platform for residents, visitors,
building operators and property developers. The current prototype combines
smart-home control, automation scenes, visitor access, tenant permissions,
building services, billing demonstrations, device monitoring and AI-assisted
insights in one interface.


2. FRONTEND

- React and Vite run the approved LIVLINK HTML prototype without removing its
  existing screens or interactions.
- A redesigned login and role-preview screen is included.
- The generated LIVLINK logo is used on the login screen and main application.
- Responsive owner, occupier, tenant, visitor, operator and developer views are
  available.
- The UI clearly states that the device layer is simulated and that no physical
  smart-home hardware is connected.
- Apple-inspired visual polish, accessible focus states, reduced-motion support,
  responsive layouts and mobile safety rules have been added.


3. SMART-HOME DEVICE DEMO

The prototype includes simulated controls for capabilities supported by the UI:

- Air conditioner: on/off and target temperature
- Lights: on/off and brightness
- Curtains: open/closed/position
- Smart lock: lock/unlock
- Television: on/off

Device commands follow a visible lifecycle:

REQUESTED -> short simulated delay -> ACKNOWLEDGED

The application does not claim that real hardware is connected.


4. SCENE MANAGEMENT

- Built-in scenes include Good Morning, Leaving Home, Movie Time and Sleep Mode.
- Scenes support Run now, Edit, Pause/Resume and Delete controls.
- Confirmed backend scenes are loaded from the database into the Scenes section.
- New scenes appear after confirmation without requiring a page reload.
- Backend scenes can be deleted through the API and removed from the interface.
- Simulated scene execution shows device acknowledgement feedback.


5. NATURAL-LANGUAGE SCENE CREATION

- Residents can describe a desired scene in plain language.
- A deterministic offline phrase matcher interprets supported requests.
- Supported requests produce a reviewable scene draft.
- Device, value and permission checks run before confirmation.
- The resident must confirm the draft before it is saved or executed.
- Unsupported or unclear requests fall back to the visual scene builder.
- Confirmed scenes are persisted in PostgreSQL.
- A simulated resident-arrival event can trigger a confirmed arrival scene.

This prototype does not use an external LLM or AI API. The current natural-
language implementation uses a seeded offline matcher with 15 phrase groups.


6. AI INTELLIGENCE FEATURES

The Home dashboard contains an AI Intelligence panel backed by the local
FastAPI application.

Implemented intelligence features:

- Energy anomaly detection compares current consumption with historical usage.
- Predictive-maintenance scoring considers battery level, battery trend,
  connection failures, repeated errors and heartbeat gaps.
- Learned automation counts repeated arrival-and-device-action patterns and can
  suggest a Welcome Home scene.
- Natural-language scene creation converts supported phrases into validated
  automation drafts.
- Insight cards can be dismissed, and automation suggestions can be accepted.
- Accepted automation suggestions create saved scenes.

All current analysis is deterministic and offline. This limitation is stated in
the interface and documentation.


7. END-TO-END LOW-BATTERY MAINTENANCE FLOW

The low-battery demonstration now runs through the backend from beginning to
end:

1. The in-process device simulator publishes a 10% smart-lock battery event.
2. The event subscriber stores the telemetry in the database.
3. The maintenance service analyses the latest five battery readings and the
   current connection-failure count.
4. When the battery is at or below 10%, the backend creates a persisted operator
   maintenance request.
5. The resident insight explains the decision and displays:
   - Current battery percentage
   - Battery decline across five readings
   - Connection failures
   - Calculated risk
   - “Request sent to Operator”
6. The Operator maintenance queue loads the same persisted request.
7. The operator can Assign or Resolve the request.
8. Assignment and resolution update the request in the database.
9. The resident sees the latest request status after the dashboard refreshes.

The automatic action only creates a maintenance work item. It does not unlock,
control or disable the physical device. The operator keeps control of assignment
and resolution.

12. SIMULATED EVENT STREAM AND DEVICE ABSTRACTION

The hackathon version uses an in-process asyncio queue. It replaces the need for
a Mosquitto server while preserving a clear event-publisher/subscriber boundary.

Current architecture:

Simulated Publisher
  -> In-process Event Bus
  -> Telemetry Subscriber
  -> Analysis Services
  -> PostgreSQL
  -> FastAPI
  -> React Frontend

Device-command architecture:

Automation Engine
  -> DeviceService
  -> DeviceAdapter interface
  -> MockDeviceAdapter
  -> Simulated devices

Future production path:

DeviceService
  -> MQTTDeviceAdapter
  -> Real IoT Gateway
  -> Physical devices
